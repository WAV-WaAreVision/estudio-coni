# Plan 4: Publishing and maintenance — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development or superpowers:executing-plans. Checkbox steps.

**Goal:** Approved pieces are published to Instagram at the approved time (never outside the 30-minute window) as Reels labelled as AI, the publication is read back and confirmed; stuck pieces, stale spend, old files and backups are handled by scheduled maintenance; failures reach Coni (plain Spanish) or WAV (technical) through a notifier.

**Architecture:** Same layering as Plans 3a/3b: adapters in `lib/proveedores/`, orchestration in `lib/publicacion/` and `lib/mantenimiento/` with injected dependencies, thin Trigger.dev v4 tasks in `trigger/` (`schedules.task` crons). External services are mocked (MSW) or faked in tests; the local Supabase is used for integration tests.

**Sources:** design doc `~/Projects/coni-heygen/docs/designs/plataforma-coni.md`: "Fecha de publicación", "Reintentos seguros", "Avisos a Coni", D3/R1 (Graph API direct, `publicar-pendientes` every 5 min, `is_ai_generated`, read-back), A3 (late approved time never published), A6 (Meta app, token renewal), A9 (immediate alerts + 08:30 digest), A10 (reconcile `en_render` > 15 min), D5 (R2 retention), D6 (nightly `pg_dump` to R2, 30 days, alert on empty or < 80 % of previous), Q4 (UTC storage, `America/Santiago`). Execution notes of Plans 1, 2, 3a, 3b (carried items listed there).

**Rules:** Verify every Instagram Graph API call (Reels container create, status polling, `media_publish`, read-back fields, AI label field name, token refresh endpoint) against Meta's official docs with WebFetch and cite the URL above each call; if the AI label cannot be set through the API, implement the rest, mark the gap and report it. Never call real Meta, Resend, R2 or HeyGen. TDD, one commit per task, lint/type/test:run/test:db separately before each commit. No `as any`, `@ts-expect-error`, non-null assertions, silent catches. Coni-facing text in Chilean Spanish without em dashes.

### Task 1: Instagram adapter (T8)
`lib/proveedores/instagram.ts`: `crearContenedorReel({ token, cuentaId, videoUrl, texto, esAvatar })` (AI label set when `esAvatar`), `estadoContenedor`, `publicarContenedor` → `mediaId`, `leerPublicacion(mediaId)` (permalink, caption, AI label as returned), `renovarToken`. Error classes: expired/invalid token → `FallaDeConfiguracion` (and a typed `TokenVencido`), 4xx definitive → `FallaDeConfiguracion`, rate limit/5xx → plain `Error`, Coni-facing message for publish failures. MSW tests for each call and error. Commit "feat(proveedores): Instagram Graph API for Reels".

### Task 2: `publicar-pendientes` (T8)
`lib/publicacion/publicar.ts` `publicarPendientes(deps, ahora)`: select `programado` pieces with `puerta2_publicar_en <= ahora` using `for update skip locked` (via an SQL function `tomar_para_publicar(p_ahora)` in a new migration, service_role only, so two cron runs never take the same piece). Per piece: `puedePublicar(pieza, { hashTexto: hashTexto(texto), ahora })`; `hora_vencida` → `transicionar(hora_vencida)` + notify Coni; `antes_de_hora` skip; ok → signed R2 URL (`urlFirmada`, 1 h) → container → poll until finished (bounded) → publish → read back: caption must equal the approved text and, for avatar pieces, the AI label must be present; on success `transicionar(publicado)` and store `media_id`/`permalink` (migration adds columns); on failure `falla_publicacion` with explanation + notify. Never publish when the read-back can't be verified: mark `falla_publicacion` (WAV checks). Store the container id before publishing so a retry does not create a second container. `trigger/publicar-pendientes.ts`: `schedules.task` cron `*/5 * * * *`, `queue: { concurrencyLimit: 1 }`. Integration tests: on time → publicado; 31 min late → video_por_aprobar; read-back missing label → falla; container id reused on retry; two concurrent runs don't double-publish. Commit "feat(publicacion): publish approved reels on time".

### Task 4: `mantenimiento` (T10, carried items)
`lib/mantenimiento/*.ts` + `trigger/mantenimiento.ts` (`schedules.task`, every 10 min for reconciliation; nightly 03:00 America/Santiago for the rest — two schedules or one task with branches):
- Reconcile `en_render` older than 15 min with a `render_id`: re-trigger `grabar-pieza` logic (read status, continue) — and `en_render`/`subtitulando` with no progress for 60 min → `falla_produccion` with explanation + notify.
- Stale spend: `reservado` rows older than 1 h whose piece already moved past the step → confirm at estimate; others older than 24 h → release.

### Gaps

- **The AI label can be set and read back through the API.** `is_ai_generated` goes in the container (avatar videos only) and comes back as a field of the published media; the post counts as published only if the read-back is a Reel, has the approved caption and shows `is_ai_generated: true`. What cannot be done is checking the label before `media_publish`: the container does not expose it, and Instagram has no API to delete or edit a published media. If Instagram ignored the flag, the reel would be live for the minutes between publishing and the alert, and the piece goes to `error_publicacion` with WAV and Coni told (tested).
- **`media_publish` is not documented as safe to repeat.** The container id is saved before polling; `publicacion_enviada_en` is saved before the call and never cleared by a retry; a piece with it set and no `media_id` is resolved by reading the container first (`PUBLISHED` means Instagram did publish: the piece goes to `error_publicacion` for WAV, never to another `media_publish`; `FINISHED` means it did not, and the same container is published again; `ERROR` or `EXPIRED` starts over with a new container). The docs name no field that gives the media id of a container, and the media-list edge (`GET /<IG_ID>/media`) is only documented on `graph.facebook.com` with Facebook Login permissions, so a post whose answer was lost cannot be recovered automatically: WAV links it by hand.
- Meta's POST examples do not show how the token travels; it is sent as the documented `access_token` parameter, in the JSON body for POSTs and in the query for GETs (the examples of the ig-media page), and it never reaches a message.
- The caption comparison trims and normalises line endings only. Whether Instagram changes anything else in a caption (it may) is unknown and would show up as a `falla_publicacion` with the post live; to be checked with a real account.
- Resend's error body is not documented; the code reads `message` when the body is JSON and the raw text otherwise.
- `postgresClient17()` in `trigger.config.ts` (PGDG apt repository) was never built: it only runs on a Trigger.dev deploy and the base image is not documented. It exists because `pg_dump` refuses a server newer than itself and Supabase runs 17; the plan's `aptGet` of `postgresql-client` would give the distribution's older client.
- The cron schedules, `onFailure` hooks, the wait-free sleep of `publicar-pendientes` and the idempotent trigger of `grabar-pieza` from `mantenimiento` are only checked as configuration, not run on Trigger.dev.

### Deviations

- Task 1: Instagram API with Instagram Login (design D3): host `graph.instagram.com`, `v25.0`. Errors are classified by Meta's `error.code` first and by HTTP status after (rate limits arrive as HTTP 400). `TokenVencido extends FallaDeConfiguracion` carries `paraConi` ("conecta de nuevo tu cuenta", `EXPLICACION_RECONECTAR`). Signed URLs lose their query string in any message.
- Task 2: `publicarPendientes(deps)` takes the clock as `deps.ahora()` (it is needed again right before publishing), not as a second argument. A lease replaces relying on `for update skip locked` alone, because that lock is gone when the function returns: `tomar_para_publicar` takes one due `programado` piece, sets `publicacion_reclamada_hasta` (10 minutes, longer than the cron) and bumps `version`, so a second run, a retry or a run that died never takes the same piece (mutation-checked: without the lease six tests fail). A piece that has to wait (container still processing, temporary Instagram failure) keeps its lease and is taken again by a later run while the window lasts; a retry at minute 26 is therefore not a concern, since the task has `retry: { maxAttempts: 1 }` and the window is re-checked with a fresh clock right before `media_publish`. The container is reused only when `contenedor_clave` equals the key of the current approval (`hashPuerta2` of video, caption hash and time, plus `intento`). `media_id` is saved before the read-back and, when set, the piece is only verified, never created or published again (also past the 30-minute window: what is live is live). A temporary failure leaves the piece `programado` and is raised at the end of the run as an `AggregateError` (WAV is told by `onFailure`); definitive ones (expired token, rejected call, container ERROR, failed read-back, caption or video changed after approval) end in `falla_publicacion` with a Coni explanation and a WAV alert; a missing Meta token or account id is treated as "reconnect Instagram". Every piece is an avatar video for now (`ES_AVATAR`), until clips of her own exist. New columns: `contenedor_id`, `contenedor_clave`, `publicacion_enviada_en`, `media_id`, `permalink`, `publicacion_reclamada_hasta` on `piezas` and `meta_cuenta_id` on `ajustes`; the Meta token stays the Vault secret `meta`. The signed R2 URL lasts 1 hour; polling is once a minute, five times per run. The `Notificador` port and `notificadorEnMemoria` were introduced here (the publish code needs them) and Resend came in task 3. New `hashPuerta2` in `lib/dominio/puertas.ts`.
- Task 3: both kinds of notice are emailed at once; `urgente` only changes the subject, because the 08:30 summary needs the notifications table of the app (Plan 5). Variables: `RESEND_API_KEY`, `AVISOS_REMITENTE`, `AVISOS_CORREO_CONI`, `AVISOS_CORREO_WAV`. The `onFailure` hook (`alFallarDeTarea`, `lib/produccion/fallas.ts`) runs after the retries are over: a piece left in `en_render` or `subtitulando` goes to `error_produccion` with a generic explanation (Coni can retry it), one left in `guion_en_proceso` only gets an `explicacion` (that state has no error state), a piece that already moved on is not touched, and an error that is a `Falla` is shown to Coni with its own message. The hooks do not release open reservations: the sweeper decides, since a video may already have been created and charged. If one alert cannot be sent the other still goes out and the failure is raised.
- Task 4: two schedules, `mantenimiento-frecuente` (every 10 minutes: renders and the spend sweeper, which the plan placed in the nightly one but whose stale reservations count against the cap in the meantime) and `mantenimiento-nocturno` (03:00 America/Santiago: retention, token, backup). Each job runs on its own and the failures are raised together. Reconciliation reads the video by `render_id` and resumes `grabar-pieza` (idempotency key per piece, attempt, state and render; scope global; TTL 1 day) only when HeyGen finished or failed it, never while it is still processing, so a live run waiting for its callback is not doubled; one hour without progress gives up with `falla_produccion`, Coni told. A piece waiting for the spending cap (`explicacion` set, no render) is left alone. The spend sweeper confirms at the estimate when the piece is past the step (HeyGen: `render_id` set or state past `en_render`; Claude and ElevenLabs: past the script) and releases after 24 hours otherwise. Retention uses `actualizada_en` as the moment a piece became published or discarded (nothing writes to them afterwards), marks `archivos_borrados_en`, refuses any key outside `videos/<id>/` and `voces/<id>/` of that piece, and keeps the voice of published pieces. The token is renewed with fewer than 10 days left or an unknown date; `guardar_token_meta` replaces the Vault secret and `meta_token_expira_en` in one transaction. The backup is `pg_dump` of the `public` and `auth` schemas (Vault is left out: its key does not travel in a dump), gzipped while it streams, to `respaldos/AAAA-MM-DD.sql.gz` (day in Santiago), 30 days kept, WAV alerted when it fails, is empty (not stored) or is under 80 % of the previous day; it relies on R2's encryption at rest (design D6 says "cifrada"). `Almacen.listar` was added for it.
