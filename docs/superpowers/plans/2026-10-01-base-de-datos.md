# Plan 2: Database layer — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A local Supabase schema where the two human gates are enforced by the database itself: only Coni can write approvals or move a piece into `en_render` or `programado`, every write is audited with its actor, the monthly spend cap is reserved atomically, Coni's API keys live in Vault and only server tasks can read them.

**Architecture:** The TypeScript domain (`lib/dominio/estados.ts`, `puertas.ts`) stays the single source of truth for transitions; the database is the safety net. Server code reads a row, runs `transicionar`, and writes the result with `update ... where id = $1 and version = $old`. Triggers enforce the invariants no caller may break (version + 1, who approves, who enters gate states, append-only audit). Integration tests talk to the local database with `pg`, impersonating Coni, the WAV maintainer, an unrelated user and `service_role` exactly as PostgREST does (`set local role` + `request.jwt.claims`).

**Tech Stack:** Supabase CLI 2.117 (local, Docker), Postgres 17, Supabase Vault, node-postgres (`pg`), Vitest 4.

**Design sources:** `~/Projects/coni-heygen/docs/designs/plataforma-coni.md`: "Las puertas, a prueba de errores", "Tope de gasto", "Seguridad y cuentas", A7 (Vault + `security definer` only for `service_role`; the maintainer never approves or acts on pieces), A8 (actor on every write, `intervenciones` for out-of-app actions), P3 (indexes), R1-33 (atomic reservation). Plan 1 execution notes for carried items.

**Scope:** T3, T14, T17 (table and access rules; the admin screen is Plan 5). No cloud accounts. Metrics tables are Plan 6.

**Conventions (same as Plan 1):** domain identifiers in Spanish; comments, commit messages and docs in English; Coni-facing strings in Chilean Spanish without em dashes; Biome safe mode only; no `as any`, `@ts-expect-error`, non-null assertions or silent catches; every commit preceded by `pnpm lint`, `pnpm type` and the relevant tests, run as separate commands. A shell hook blocks commands containing the text `pnpm dev`.

```ts
import pg from "pg"

export const URL_DB = process.env.SUPABASE_DB_URL ?? "postgresql://postgres:postgres@127.0.0.1:54422/postgres"

export const CONI = "c0000000-0000-4000-8000-000000000001"
export const MANTENEDOR = "a0000000-0000-4000-8000-000000000002"
export const OTRA = "b0000000-0000-4000-8000-000000000003"

export type Sesion = { tipo: "usuario"; id: string } | { tipo: "servicio" } | { tipo: "postgres" }

export const comoConi: Sesion = { tipo: "usuario", id: CONI }
export const comoMantenedor: Sesion = { tipo: "usuario", id: MANTENEDOR }
export const comoOtra: Sesion = { tipo: "usuario", id: OTRA }
export const comoServicio: Sesion = { tipo: "servicio" }
export const comoPostgres: Sesion = { tipo: "postgres" }

export const pool = new pg.Pool({ connectionString: URL_DB, max: 4 })

/** Impersonates an actor the way PostgREST does, for the current transaction only. */
export async function asumir(cliente: pg.PoolClient, sesion: Sesion): Promise<void> {
  if (sesion.tipo === "postgres") return
  const claims =
    sesion.tipo === "usuario" ? { sub: sesion.id, role: "authenticated" } : { role: "service_role" }
  await cliente.query("select set_config('request.jwt.claims', $1, true)", [JSON.stringify(claims)])
  await cliente.query(`set local role ${sesion.tipo === "usuario" ? "authenticated" : "service_role"}`)
}

/** Runs `fn` as `sesion` inside a transaction that is always rolled back, so tests leave no data behind. */
export async function como<T>(sesion: Sesion, fn: (cliente: pg.PoolClient) => Promise<T>): Promise<T> {
  const cliente = await pool.connect()
  try {
    await cliente.query("begin")
    await asumir(cliente, sesion)
    return await fn(cliente)
  } finally {
    await cliente.query("rollback")
    cliente.release()
  }
}
```

language sql stable security definer set search_path = '' as $$

### Task 3: Gates and audit in the database (T3, part 2)

**Files:** Create `supabase/migrations/20261001000300_puertas_y_auditoria.sql`, `tests/integration/puertas.test.ts`, `tests/integration/auditoria.test.ts`.

Rules enforced on every `piezas` update, whoever writes (`service_role` and SQL editor included):
1. `version` must be exactly `old.version + 1` (optimistic lock; every write is a new version, so a hash computed from a row read at version N is valid for the update that requires version N).
2. Writing a non-null approval that differs from the old one (gate 1: `puerta1_hash`; gate 2: any of `puerta2_video_id`, `puerta2_hash_texto`, `puerta2_publicar_en`) requires `es_coni()`. The trigger sets `puerta1_por` / `puerta2_por` to `auth.uid()` itself (callers cannot forge them) and clears them when the hash is cleared. Clearing approvals is allowed for tasks (invalidations).
3. Entering `en_render` or `programado` requires `es_coni()` (tasks never enter those states; Coni approves, re-records or retries).
4. Inserts start at `version = 0` with no approvals.
5. `eventos` and `intervenciones` are append-only for everyone.
6. Every insert, update and delete on `piezas`, `ideas`, `ajustes`, `gastos` and `intervenciones` writes an `eventos` row with `actor_usuario = auth.uid()`, `actor_rol = coalesce(request.jwt.claims ->> 'role', current_user)`, `pieza_id` when the table has one, and `datos` = the new row (old row on delete).

language plpgsql set search_path = '' as $$
declare
  aprueba_puerta1 boolean;
  aprueba_puerta2 boolean;
begin
  if tg_op = 'INSERT' then
    if new.version <> 0 or new.puerta1_hash is not null or new.puerta2_hash_texto is not null then
      raise exception using errcode = '42501', message = 'pieza_nueva_invalida';
    end if;
    return new;
  end if;

  if new.version <> old.version + 1 then
    raise exception using errcode = '40001', message = 'version_desfasada';
  end if;

  aprueba_puerta1 := new.puerta1_hash is not null and new.puerta1_hash is distinct from old.puerta1_hash;
  aprueba_puerta2 := new.puerta2_hash_texto is not null and (
    new.puerta2_hash_texto is distinct from old.puerta2_hash_texto
    or new.puerta2_video_id is distinct from old.puerta2_video_id
    or new.puerta2_publicar_en is distinct from old.puerta2_publicar_en
  );
  if (aprueba_puerta1 or aprueba_puerta2) and not public.es_coni() then
    raise exception using errcode = '42501', message = 'solo_coni_aprueba';
  end if;

    raise exception using errcode = '42501', message = 'solo_coni_entra_a_puerta';
  end if;

  -- Who approved is recorded by the database, never taken from the caller.
  if aprueba_puerta1 then
    new.puerta1_por := auth.uid();

    new.puerta1_por := null;
  else
    new.puerta1_por := old.puerta1_por;
  end if;
  if aprueba_puerta2 then
    new.puerta2_por := auth.uid();
  elsif new.puerta2_hash_texto is null then
    new.puerta2_por := null;
  else
    new.puerta2_por := old.puerta2_por;
  end if;

  new.actualizada_en := now();
  return new;
end $$;

```sql
create function public.reservar_gasto(
  p_pieza uuid,
  p_proveedor text,
  p_paso text,
  p_estimado numeric,
  p_clave text,
  p_ahora timestamptz default now()
) returns public.gastos
language plpgsql set search_path = '' as $$
declare
  v_mes date := date_trunc('month', p_ahora at time zone 'America/Santiago')::date;
  v_existente public.gastos;
  v_tope numeric;
  v_usado numeric;
  v_nuevo public.gastos;
begin
  -- One reservation at a time per month, so two renders started together cannot both pass the cap.
  perform pg_advisory_xact_lock(hashtext('gastos:' || v_mes::text));

  select * into v_existente from public.gastos where clave = p_clave;
  if found then
    return v_existente;
  end if;

  select tope_mensual_usd into v_tope from public.ajustes where id;
  select coalesce(sum(coalesce(real_usd, estimado_usd)), 0) into v_usado
    from public.gastos where mes = v_mes and estado in ('reservado', 'confirmado');
  if v_usado + p_estimado > v_tope then
    raise exception using errcode = 'P0001', message = 'tope_alcanzado',
      detail = format('usado=%s estimado=%s tope=%s', v_usado, p_estimado, v_tope);
  end if;

  insert into public.gastos (pieza_id, proveedor, paso, mes, estimado_usd, clave)
  values (p_pieza, p_proveedor, p_paso, v_mes, p_estimado, p_clave)
  returning * into v_nuevo;
  return v_nuevo;
end $$;

create function public.confirmar_gasto(p_clave text, p_real numeric) returns public.gastos
language sql set search_path = '' as $$
  update public.gastos set estado = 'confirmado', real_usd = p_real
  where clave = p_clave and estado = 'reservado'
  returning *
$$;

create function public.liberar_gasto(p_clave text) returns public.gastos
language sql set search_path = '' as $$
  update public.gastos set estado = 'liberado'
  where clave = p_clave and estado = 'reservado'
  returning *
$$;

revoke execute on function public.reservar_gasto(uuid, text, text, numeric, text, timestamptz),
  public.confirmar_gasto(text, numeric), public.liberar_gasto(text) from public, anon, authenticated;
grant execute on function public.reservar_gasto(uuid, text, text, numeric, text, timestamptz),
  public.confirmar_gasto(text, numeric), public.liberar_gasto(text) to service_role;
```

create function public.guardar_secreto(p_nombre text, p_valor text) returns void
language plpgsql security definer set search_path = '' as $$
declare
  v_id uuid;
begin

  end if;
end $$;

language sql security definer set search_path = '' as $$

$$;

grant execute on function public.leer_secreto(text) to service_role;

### Limits worth knowing

- The `postgres` role (SQL editor, owner) can still bypass every trigger on purpose with `set session_replication_role = replica` or `alter table ... disable trigger`. `service_role` and `authenticated` cannot (tested: `42501` and "must be owner"). The gates protect against the app, the tasks and PostgREST callers, not against someone holding the database owner credentials.
- The database gates entry to `en_render` and `programado` and the writing of approvals; it does not validate transitions. Only `transicionar` knows the table, so every writer must go through it.
- The concurrency test commits two `gastos` rows and deletes them; their audit rows in `eventos` stay (append-only) until the next `supabase db reset`.
